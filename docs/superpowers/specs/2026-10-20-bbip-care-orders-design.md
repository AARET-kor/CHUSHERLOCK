# BBIP 처방·드레싱·F/U 오더 설계

- 작성일: 2026-10-20
- 기반: `main` @7630b4d (BBIP core + 문헌 + 해부 지도 + 에디토리얼 리디자인)
- 상위 설계: `docs/superpowers/specs/2026-10-18-bbip-design.md`
- 상태: 설계 확정 (사용자 승인 2026-10-20), 구현 계획 `docs/superpowers/plans/2026-10-20-bbip-care-orders.md`

## 1. 목표

시술을 정한 뒤, 원장이 바로 처리할 수 있는 **시술 후 오더**를 만든다.

1. **처방** — 어떤 약을, 왜, 얼마나, 얼마 동안.
2. **드레싱·처치** — 재료, 방법, 교체 주기, 기간.
3. **상황별 대처 (이럴 때는)** — 이런 상황·징후면 이 약/처치를 쓰고, 보통 이렇게 해결되며, 긴급도는 이렇다. 예: HSV 재발, 감염 징후, 멍·부종, 혈관 폐색 의심.
4. **F/U** — 언제 다시 보고(D+1, D+7 …) 무엇을 확인하며, 다음 회차는 무엇인지.

원장이 행마다 확인하면 두 가지 결과물이 나온다.

- **EMR 오더 텍스트** — 한 번에 복사해서 EMR에 붙여넣는다.
- **환자 안내문** — 쉬운 말로 쓴 약 복용법, 드레싱 방법, "이럴 땐 이렇게 / 바로 연락", 다음 내원일. 인쇄하거나 복사해서 카톡으로 보낸다.

확인한 오더는 시술별 **내 처방 세트**로 저장한다. 다음에 같은 시술이면 세트가 먼저 나오고, AI는 이 케이스에 맞춘 조정만 제안한다.

### 하지 않는 것

- 앱 안의 F/U 예약·리콜 목록, 시술 기록(차팅) 템플릿, EMR 연동.
- 환자 식별정보 저장. 안내문에도 이름을 넣지 않는다.
- 일괄 "모두 확인" 버튼. 행마다 원장이 직접 확인한다.

## 2. 사용자 흐름

```
 03 더 보기   … 섹션 인덱스 …
             문헌     문헌 근거 찾기                         →
             오더     처방·드레싱·F/U  (누를 때만 작성)      →

 04 처방·F/U  ⚠ 이 케이스 주의: 아스피린 복용 — NSAID 피하고 아세트아미노펜
             처방
             [✓] 무피로신 2% 연고 · 1일 3회 도포 · 5일 · 감염 예방     노트 2
             [ ] 발라시클로버 500 mg 정 · 1일 2회 · 5일 · HSV 예방      AI 제안 수치 — 확인 필요
             드레싱·처치
             [ ] 재생크림 · 세안 후 얇게 · 1일 2회 · 7일                 내 세트
             이럴 때는
             [ ] 수포·작열감(HSV 재발 의심) → 항바이러스제 시작 → 바로 연락
             F/U
             [ ] D+7 · 홍반·색소 침착 확인 · 2회차 일정
             ─────────────────────────────────────────
             EMR 오더 복사 (모든 행 확인 후)   환자 안내문   내 세트로 저장
```

1. **더 보기** 인덱스에 "오더 — 처방·드레싱·F/U" 행이 있다. 누를 때만 작성한다. 문헌 근거와 같은 방식이다.
2. 케이스의 시술 칩에 **내 세트**가 있으면 세트 행으로 시작한다. AI는 세트를 보고 이 케이스에 맞춘 조정만 제안한다. 빼야 할 세트 행은 사유와 함께 "제외"로 표시하고 되살릴 수 있다. 더할 행은 새 행으로 붙인다.
3. 세트가 없으면 AI가 처음부터 초안을 쓴다 (Opus, 구조화 출력).
4. 결과는 네 개의 표로 보인다. 각 행에는 확인 체크, 수정, 삭제가 있고, 표마다 행을 추가할 수 있다.
5. 모든 행이 확인되면 "EMR 오더 복사"가 켜진다. "환자 안내문"은 확인된 행만으로 만든 인쇄용 페이지를 연다.
6. "내 세트로 저장"은 확인된 행을 시술 칩 하나(여러 개면 고른다)의 세트로 저장한다. 같은 시술의 세트가 있으면 덮어쓴다.

## 3. 행의 구조

행은 종류마다 정해진 칸을 가진다. 모든 칸은 문자열이고, 안 쓰는 칸은 빈 문자열이다.

| 종류 | 칸 (필수는 *) |
|---|---|
| 처방 `rx` | 성분명*, 상품명 예, 제형·함량*, 1회량*, 횟수*, 기간*, 목적 |
| 드레싱·처치 `dressing` | 재료*, 방법*, 교체 주기, 기간 |
| 이럴 때는 `contingency` | 상황*, 징후, 조치*, 경과·해결, 긴급도* (`now` 바로 연락·내원 / `followup` 다음 내원 때 / `watch` 지켜봐도 됨) |
| F/U `followup` | 시술 후 일수(정수), 시점*, 확인 항목*, 다음 계획 |

행마다 함께 저장하는 것:

- **환자 문장(patientText)** — 안내문에 들어갈 쉬운 말. **용량·횟수·기간 숫자는 넣지 않는다.** 안내문은 숫자를 칸에서 가져오므로, 원장이 칸을 고치면 안내문도 같이 맞는다.
- **출처** — `set`(내 세트) / `note`(노트 n) / `literature`(P#·W#) / `ai`. 인용 표시는 기존 각주 방식(`2`, `P1`, `W1`, *AI*)을 따른다.
- **확인 여부**, 그리고 세트 행을 AI가 빼자고 했다면 **제외 사유**.

## 4. 안전 장치

### 4.1 숫자 규칙의 범위

BBIP의 기존 규칙인 "[AI] 문장에는 수치 금지"는 산문 카드에 그대로 남는다. **수치는 이 오더의 구조화된 칸에서만 허용**한다. 이 칸은 원장 확인을 거쳐야만 복사·안내문으로 나간다.

- AI 출처 행에 숫자가 있으면 **"AI 제안 수치 — 확인 필요"** 표시가 확인 전까지 붙는다.
- 허가 범위 밖 사용(오프라벨)이면 AI는 목적 칸에 그 사실을 적는다.

### 4.2 결정론적 검사 (코드, AI 아님)

**상호작용·금기 경고** — `lib/bbip/care/interactions.ts`의 작은 규칙표. 케이스 텍스트(칩 + 플래그)와 행의 약 이름을 대조한다.

| 케이스 | 약 | 수준 |
|---|---|---|
| 임신·수유 | 테트라사이클린계 | 금기 |
| 임신·수유 | 레티노이드 (이소트레티노인·트레티노인·아다팔렌) | 금기 |
| 항응고·항혈소판제 | NSAID | 주의 (아세트아미노펜 고려) |
| 와파린 | 메트로니다졸·플루코나졸·퀴놀론·마크롤라이드 | 주의 (INR 상승) |
| 이소트레티노인 | 테트라사이클린계 | 금기 (두개내압 상승) |
| 페니실린 알레르기 | 페니실린계 | 금기 |
| 페니실린 알레르기 | 세팔로스포린 | 주의 |

규칙표는 해부 아틀라스처럼 **"원장 검토 전 초안"** 배지를 달고 `reviewedBy/reviewedAt`을 파일에 기록한다.

**형식 검사**

- 오류(확인 불가): 필수 칸이 비어 있음, 긴급도 값이 잘못됨, F/U 일수가 정수가 아님.
- 경고(확인은 가능): 경구 제형인데 1회량에 숫자+단위가 없음, 처방 행의 환자 문장에 숫자가 있음(칸과 어긋날 수 있음), AI 제안 수치.

**확인 규칙**

- 오류가 있는 행은 확인할 수 없다. 칸을 고치면 확인이 풀린다.
- 세트에서 온 행은 경고가 없으면 확인된 상태로 시작한다(이미 원장이 확정했던 값). 상호작용 경고가 걸리면 확인되지 않은 상태로 시작한다.
- 복사·안내문·세트 저장은 **제외되지 않은 모든 행이 확인됐을 때만** 가능하다. 서버도 같은 조건을 다시 검사한다.

### 5.2 데이터 (Drizzle 마이그레이션 1개, `0013`)

```
bbip_care_orders
  id, session_id → bbip_sessions (cascade, unique), items json(CareItem[]),
  set_keys json(string[]), caution text, model, created_at, updated_at
bbip_care_sets
  id, procedure_key (unique), label, items json(CareItem[]),
  source_session_id?, updated_at
```

- 세션당 주문은 하나다. 다시 작성하면 바꾼다. 확인된 행이 있으면 다시 작성 전에 원장에게 묻는다.
- 세트 행은 출처를 `set`으로, 인용을 비워서 저장한다. 노트 번호는 세션마다 다르기 때문이다.

### 5.3 생성

- 모델: `BBIP_CARE_MODEL`, 기본은 `CODEX_AI_MODEL`(Opus 5.5). effort `medium`. Opus 5.x·Sonnet 5.5면 서버측 폴백("default")을 쓴다.
- `output_config.format`의 JSON 스키마로 받는다. 행은 평평한 객체 하나에 모든 칸을 담고, 종류별로 칸을 골라 쓴다.
- 프롬프트: 정적 케어 시스템 프롬프트(캐시) → 케이스 + 노트(+ 문헌) 블록 → `<myset>` 블록(세트가 있을 때) → 지시문.
- 응답: `{ caution, items[], remove[{id, reason}] }`. 세트가 없으면 `remove`는 비어 있다.
- 응답 검증: 스키마에 맞지 않는 행은 버리고 카드에 "형식이 맞지 않는 n개 행을 뺐습니다"라고 알린다. 존재하지 않는 노트 번호나 P#/W# 인용은 AI 출처로 바꾼다. 검토 전 BBIP 초안 노트를 인용해도 AI 출처다.
- 요청은 스트리밍 SDK 호출에 `finalMessage()`를 써서 받는다. 클라이언트에는 JSON 한 번으로 돌려준다(카드는 "작성 중" 표시).

### 5.4 결과물

- **EMR 오더 텍스트**: `[처방]`, `[드레싱·처치]`, `[이럴 때는]`, `[F/U]` 순서. 제외된 행은 빠진다. 각 줄은 칸에서 결정론적으로 만든다.
- **환자 안내문**: "드실 약·바르실 약", "상처 관리", "이럴 땐 이렇게 하세요", "다음 내원". 약 줄은 칸(1회량·횟수·기간)과 환자 문장을 합친다. 긴급도는 문구로 바꾼다. `now`는 "바로 병원으로 연락하세요", `followup`은 "다음 내원 때 말씀해 주세요", `watch`는 "대부분 저절로 좋아집니다". F/U 일수가 있으면 오늘 날짜를 기준으로 날짜를 적는다(예: "10월 27일(화)").
- 안내문 페이지는 인쇄용이고 상단 내비게이션은 인쇄되지 않는다. 텍스트 복사 버튼이 있다.

## 6. 에러 처리

| 상황 | 동작 |
|---|---|
| 생성 실패·타임아웃·거절 | 카드에 오류와 다시 시도. 주문을 저장하지 않음 |
| 일부 행이 스키마 불일치 | 그 행만 버리고 알림 |
| 세트만 있고 AI 조정 실패 | 세트 행만으로 주문을 만들고 "AI 조정 실패 — 세트만 표시" 알림 |
| 미확인 행이 있는데 복사·세트 저장 요청 | 버튼 비활성 + 서버 409 |
| fake 모드 | 결정론적 4행 오더(세트가 있으면 조정 없음) |

## 7. 테스트

**단위 (Vitest, 오프라인)**: `fields`(필수 칸), `interactions`(규칙별 매칭과 비매칭), `lint`(오류·경고·확인 조건·`orderReady`), `format`(EMR 텍스트 순서, 제외·미확인 처리, 안내문 문구, 날짜), `sets`(키 정규화, 시드 중복 제거, 세트 저장 변환), `prompt`(블록, 태그 무력화, 스키마), `parse`(출처·인용 검증, 잘못된 행 제거, remove 처리), `generate`(주입한 호출로 파라미터·폴백·거절 처리, fake), `careService`(DB 왕복, 세션당 하나, 세트 덮어쓰기), API(작성·PATCH 검증·미확인 시 409·세트 저장·삭제).

**E2E (Playwright, fake 모드)**: 케이스 → "처방·드레싱·F/U" → 행 확인 → EMR 오더 복사 → 환자 안내문 페이지 → 내 세트로 저장 → 같은 시술의 새 케이스에서 세트 행이 "내 세트"로, 확인된 상태로 나온다. Axe 검사도 포함한다.

## 8. 이후 (v2 후보)

- 앱 안의 F/U 리콜 목록(식별정보 없이 세션 기준).
- 시술 기록(차팅) 템플릿.
- 세트 편집 화면(지금은 오더에서 저장·덮어쓰기와 목록 삭제만).
- 상호작용 규칙표를 원장이 앱 안에서 편집.
